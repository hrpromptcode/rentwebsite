## Follow-ups for other packets

- commerce (packages/modules/commerce/test/orders.test.ts:156): the test expects the guest customer row to carry `email: "somchai@example.com"`. By design (SS-02) a guest record is now keyed by the phone only and the e-mail stays on the order, so change that expectation to `email: null` (and assert the e-mail on the order row instead). That assertion throws inside the test transaction, which rolls back markPaid, so the next test ("cancelUnpaidOrder ... paid orders cannot be cancelled") fails as a knock-on. The booking, restaurant, topup, db and core suites are green.
- payments (packages/core/src/payments enabledMethods): when nothing is configured it falls back to 'slip' even with zero bank accounts; new tenants now start without receivers, so checkout should block / hide payment until the owner sets PromptPay or a bank account (AC-02).
- integrations handlers.ts: owner notifications use settings.contact.email (now blank for new tenants); fall back to the owner account e-mail (tenant_members owner -> user.email) so new owners still get order/form e-mails (AC-02/AC-03).
- admin dashboard queries.ts checklist is value-based and now correct for new tenants; consider also basing it on onboarding.steps only as AC-02 suggests.
- storefront blog: no /blog route exists; if one is added, re-add the corporate nav item and publish the seeded posts (SS-06). apps/web sitemap.xml route still emits /blog/<slug> for published posts of any tenant.

- apps/web/src/lib/customer.ts (requestMeta): IP comes from the first X-Forwarded-For entry, which a client can spoof when the app is not behind a proxy that overwrites it; per-target limits still hold. Cookie `secure` flag is derived from the host string, not the protocol (SEC-007 note).
- packages/core/src/storage.ts:76 still uses Math.random for object-key randomness (SEC-006 second half) -> use randomUUID/randomBytes.
- packages/integrations/src/events/handlers.ts customerTarget prefers customers.email/phone over the order's own contact; with guest records now keyed by one contact, prefer the order/booking contact (fallback) for order notifications.
- Legacy data: customer rows created/patched by the old guest code can still hold an unverified e-mail next to a phone (e.g. demo-cafe 0854529323 from the SS-02 repro). Consider a one-off cleanup / session revoke for such rows.
