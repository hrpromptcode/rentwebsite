## For the ADMIN fixer (packages/modules/topup/src/admin/**, apps/admin top-up pages)

Everything below is exported from `@rentweb/module-topup/services` (services/index.ts). Signatures:

* `failPaidOrder(tx, tenantId, orderId, reason, { by?: string | null }) → Result<{ order, refunded, refundRequired }, "not_found" | "not_paid" | "closed">`
  — USE THIS in `adminFailOrder` instead of `failOrder`. Fails a paid / processing / fulfilled order (the service allows fulfilled — keep the admin's own "fulfilled cannot fail" guard). Wallet → credited back (`refunded: true`, order `refunded`, payment refunded); a wallet that cannot take the credit (frozen) → manual-refund flag instead of a throw (the admin's frozen pre-check may stay). Slip / QR → order `failed` + the PAYMENT is flagged (`flagTopupPaymentRefund`). Emits `topup.failed` itself. Map: `not_paid` → "รายการยังไม่ชำระเงิน — ใช้ “ยกเลิกรายการ” แทน", `closed` → "รายการนี้ปิดไปแล้ว", `not_found`. Pass `{ by: actor.userId }` (sets processed_by — no extra UPDATE needed).
* `failOrder(…)` (legacy) still exists: paid → like failPaidOrder; UNPAID → cancels through `cancelUnpaidTopupOrder` (never leaves the payment open); slip under review → unchanged. Admin code should not rely on it.
* `cancelUnpaidTopupOrder(tx, tenantId, orderId, { reason?, by: "admin" | "customer" | "system", actorId?, allowSlipPending?: boolean }) → Result<TopupOrder, "not_found" | "not_pending" | "slip_pending" | "paid">`
  — USE THIS in `adminCancelOrder` instead of the raw `UPDATE payments` + own emit: voids the open (or failed) payment with `cancelPayment(…, { runHandler: false })` (payment `cancelled` + `payment.cancelled`), sets the order `cancelled` (failureReason = reason or "ยกเลิกโดยแอดมิน", processed_by = actorId) and emits `topup.cancelled` (do NOT emit again). `slip_pending`: a slip waits for review → ask "ยกเลิกทั้งที่มีสลิปรอตรวจ?" and retry with `allowSlipPending: true`; `paid`: money was confirmed meanwhile → reload. Also the way to close an order whose slip was rejected (payment `failed`): such orders stay `pending_payment` (the sweep expires only `pending` payments; the shop may still re-approve a failed payment) — offer "ยกเลิกรายการ" after `adminRejectSlip`.
* `topupEventPayload(order, extras?)` — every `emitEvent(tx, { type: "topup.*" })` in admin/orders.ts must build its payload with it, e.g. adminFulfillOrder: `payload: topupEventPayload(updated!, { manual: true, proofImage: input.proofImage ?? null, hasCode: !!code })` (today it sends no gameName / packageName / contact / accessKey → empty notification text, guests not reached). adminCancelOrder's emit disappears with cancelUnpaidTopupOrder.
* `flagTopupPaymentRefund(tx, tenantId, paymentId, reason) → Promise<boolean>` — flags a paid payment for a manual refund exactly like markPaid (no-op when already flagged). Read the flag with `paymentRefundRequired(payment)` from `@rentweb/core/payments` and show it next to the payment ("ต้องคืนเงิน: …") on the order page / queue; `topupFailureText(code)` gives Thai copy for `out_of_stock` / `supplier_failed`.
* `fulfillOrder(tx, tenantId, orderId)` — api packages go through the supplier adapter (services/suppliers.ts): retrying a `processing` api order is now safe (it queries the supplier by the order number before re-submitting). An unknown outcome (timeout) keeps the order `processing` with `supplier_response.lastError` and `attempts[]` → adminRetryOrder currently answers `retry_failed`; better copy: "ยังไม่ทราบผลจากผู้ให้บริการ — กดลองใหม่ ระบบจะตรวจสอบก่อนส่งซ้ำ". Show `supplier_response.attempts` (at / action / status / ref / error) in the order timeline. `supplier_response.idempotencyKey` = order number.
* Supplier config (admin/schemas.ts topup_suppliers.config): credentials must not be stored there (contract in suppliers.ts) — refuse keys like apiKey / secret / token / password in the config JSON or move them to tenant_secrets. `registerSupplierAdapter(provider, adapter)` / `supplierAdapterFor(provider)`; without an adapter every provider uses the simulator (say "จำลอง (ยังไม่เชื่อมผู้ให้บริการจริง)" in the supplier UI).
* Player-field formats (STOREFRONT-12): `gameFieldSchema` (admin/schemas.ts) is a strict zod object → saving a game in admin STRIPS the new GameField keys. Add `pattern` (refine: `safeFieldPattern(v) !== null`, max 200), `minLength` / `maxLength` (int 1…`PLAYER_FIELD_MAX` = 120, min ≤ max), `inputMode` ("text" | "numeric"), `hint` (≤ 80, Thai format hint shown to customers and used in the error message) and inputs for them in the game field editor.
* Guest orders now have `customer_id = NULL` (STOREFRONT-05): admin order detail / list must show `order.contact` for guests (no customer link); per-customer stats only count signed-in orders.
* wallet_topups statuses: `cancelled` is new (customer cancel / cancelled payment) → add `cancelled: { label: "ยกเลิก", variant: "muted" }` to TOPUP_STATUS in apps/admin/src/app/t/[slug]/topup/wallets/[id]/page.tsx; `rejected` now also means "money arrived but could not be credited (frozen wallet …) → refund flagged on the payment".
* `adjustWallet` double submit now returns `ok({ duplicate: true })` under real concurrency (SERVICES-12) — the dialog can show "บันทึกไปแล้ว".
