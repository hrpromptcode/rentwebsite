# Module implementation guide (for engineers and AI agents)

This document is the contract for building a business module (commerce, booking, topup, restaurant, clinic…) on the RentWeb platform. Read it fully before writing code.

## 1. Where things live

```
packages/db/src/schema/<module>.ts      tables (already defined – extend only if truly needed)
packages/core/src/                      tenant ctx, theme, payments, customer auth, storage, money, events
packages/storefront/src/definitions     zod definitions for sections (already defined for your module)
packages/storefront/src/payments        <PaymentPanel/> <PaymentMethodPicker/> (shared UI)
packages/modules/<module>/
  src/services/*.ts                     pure business logic: (tx: Tx, tenantId, input) => result. NO React, NO next imports.
  src/sections/*.tsx                    React server components for storefront sections (product-grid, booking-widget…)
  src/components/*.tsx                  client components (add-to-cart, slot picker, order tracker…)
  src/register.ts                       side effects: registerSection(type, Component) + registerPaymentHandler(refType, …)
  test/*.test.ts                        vitest on PGlite via @rentweb/db/test-utils (createTestDb)
apps/web/src/app/(sites)/rw/[tenantId]/<route>/page.tsx   storefront pages (tenant host → rewritten here by proxy)
apps/web/src/app/(sites)/rw/[tenantId]/api/<module>/...   route handlers → reachable as /api/<module>/... on the tenant host
```

Only touch: your module package, your route folders under `rw/[tenantId]/`, and the template file(s) listed in your brief. Never edit `packages/storefront`, `packages/ui`, `packages/core`, `packages/i18n` or other modules — if you need a shared change, describe it in your final report and work around it locally.

## 2. Non-negotiable conventions

- **Tenant scoping**: every DB access goes through `tenantTx(tenantId, tx => …)` (web) or `withTenant(db, tenantId, …)` (core). Every query still filters `eq(table.tenantId, tenantId)`. Inserts always set `tenantId`. RLS blocks anything else.
- **Money** is integer satang. Format with `thb()` / `formatMoney()` from `@rentweb/core/money`. Never use floats.
- **IDs** are uuid v7 (generated by the schema). Human numbers (`#1001`, `BK-1001`) come from `nextCounter(tx, tenantId, "order")`.
- **Params/searchParams/cookies/headers are Promises** (Next 16): `const { tenantId } = await params`.
- **Server components by default**; `"use client"` only for interactive leaves. Server Actions (`"use server"`) for mutations; validate input with zod; call `revalidatePath()` after writes.
- **Events**: after important writes call `emitEvent(tx, { tenantId, type: "order.paid", payload })` from `@rentweb/core`. A worker will deliver notifications later — don't send email/LINE yourself.
- **Audit**: `audit(tx, {...})` for money-related or admin actions.
- **Errors**: expected failures return `Result` (`ok()/fail()` from `@rentweb/core`); never throw for stock-out / slot-taken.
- **Thai copy** for all UI text (English optional). Keep strings inside your module (a `labels.ts`), not in `@rentweb/i18n`.
- **Icons**: lucide-react only. No emoji as icons.
- **Images**: plain `<img>` via `Img` from `@rentweb/storefront` (CDN handles sizing). Always `alt`.

## 3. Storefront page skeleton

```tsx
// apps/web/src/app/(sites)/rw/[tenantId]/products/page.tsx
import { notFound } from "next/navigation";
import { getRuntime } from "@/lib/tenant";
import { buildCtx } from "@/lib/storefront-ctx";
import { getCurrentCustomer } from "@/lib/customer";
import { listProducts } from "@rentweb/module-commerce/services";

export default async function ProductsPage({ params, searchParams }: { params: Promise<{ tenantId: string }>; searchParams: Promise<Record<string, string>> }) {
  const { tenantId } = await params;
  const runtime = await getRuntime(tenantId);
  if (!runtime || !runtime.config.modules.includes("commerce")) notFound();
  const ctx = await buildCtx(runtime);                 // { tenant, theme, t, locale, origin }
  const customer = await getCurrentCustomer(tenantId); // null when signed out
  const products = await tenantTx(tenantId, (tx) => listProducts(tx, tenantId, { status: "active" }));
  return <PageBody theme={runtime.theme} sections={[]}>…</PageBody>; // PageBody adds top padding under overlay headers
}
```

`ctx.t("cart.add")` gives translated labels (see `packages/i18n/src/th.ts` for existing keys). `ctx.theme.layout.*` / `ctx.theme.effects.*` describe the tenant's look; most styling should simply use the semantic Tailwind tokens (`bg-primary`, `text-muted-foreground`, `card`, `btn` via `<Button>`), which already follow the theme.

## 4. Sections

Definitions (zod + defaults) already exist in `packages/storefront/src/definitions/index.ts` for: `product-grid`, `category-list`, `booking-widget`, `service-list`, `staff-grid`, `game-grid`, `topup-feed`, `menu-highlight`, `reservation-cta`, `package-list`. Implement the React component and register it:

```ts
// packages/modules/commerce/src/register.ts
import { registerSection } from "@rentweb/storefront";
import { registerPaymentHandler } from "@rentweb/core/payments";
import { ProductGridSection } from "./sections/product-grid";
import { onOrderPaid } from "./services/orders";

registerSection("product-grid", ProductGridSection);
registerPaymentHandler("order", onOrderPaid);
```

Component signature: `async function X({ ctx, props, id, index }: { ctx: StorefrontCtx; props: z.output<typeof productGrid.schema>; id: string; index: number })`. Load data with `withTenant(getDb(), ctx.tenant.id, …)` from `@rentweb/db` (sections render on the server). Use `Section`, `SectionHeading`, `Reveal`, `Stagger`, `TiltCard`, `Marquee`… from `@rentweb/storefront` / `@rentweb/ui/motion` so sections animate like the rest of the site. Respect `prefers-reduced-motion` (motion components already do).

## 5. Customers (storefront auth)

- `getCurrentCustomer(tenantId)` (apps/web `@/lib/customer`) → `{ id, name, phone, email, tier } | null`.
- Require login: `if (!customer) redirect(\`/account/login?next=${encodeURIComponent(path)}\`)`.
- Guest flows: `upsertGuestCustomer(tx, tenantId, { phone, email, name })` from `@rentweb/core/customer` returns a customer to attach to orders/bookings.
- Account pages live under `rw/[tenantId]/account/*` — add yours (`account/orders`, `account/bookings`, `account/topups`) and they are linked from `/account` automatically when the module is enabled.

## 6. Payments (shared)

```ts
import { createPayment, markPaid, attachSlip, resolvePromptpayId, enabledMethods, paymentSettings, promptpayQrDataUrl } from "@rentweb/core/payments";
import { PaymentPanel, PaymentMethodPicker } from "@rentweb/storefront/payments";
```

1. In the flow (checkout / booking deposit / top-up): pick a method from `enabledMethods(ctx.tenant.settings)` (+ `wallet` for top-up) using `<PaymentMethodPicker/>`.
2. On submit (server action): create your domain row (order/booking/topup_order), then `createPayment(tx, tenantId, { refType: "order", refId, amount, provider, method, customerId, promptpayId: resolvePromptpayId(settings), expiresMinutes: 30 })`. Store `paymentId` on your row.
3. Render `<PaymentPanel payment={{ id, method, status, amount, qrDataUrl: await promptpayQrDataUrl(payment.qrPayload), expiresAt }} amountLabel={thb(amount)} bankAccounts={paymentSettings(settings).bankAccounts} successHref="/orders/123" />`. The panel handles QR display, slip upload (`POST /api/payments/:id/slip`), polling (`GET /api/payments/:id`) and the paid state.
4. Your `registerPaymentHandler("order", async (tx, payment) => …)` runs inside `markPaid()`: update your row (`paymentStatus = "paid"`, decrement stock, deliver codes…) and `emitEvent`. Make it idempotent.
5. `cod` / `cash` / `wallet`: call `markPaid` yourself when appropriate (wallet: after debiting the ledger).
6. Dev: slips auto-approve when `DEV_AUTO_APPROVE_SLIPS=true` (set it in `.env` while testing) or the tenant sets `settings.payments.autoApproveSlips`.

## 7. Testing & verification

- Unit/integration: `packages/modules/<module>/test/*.test.ts` using `createTestDb()` from `@rentweb/db/test-utils` and your services. Run `pnpm --filter @rentweb/module-<module> test`.
- Typecheck: `pnpm --filter @rentweb/module-<module> --filter @rentweb/web typecheck` must pass.
- The web dev server is already running on port 3000 (do **not** start another one, do **not** run `pnpm install` unless a brand-new dependency is unavoidable — prefer what's already there: zod, drizzle, motion, lucide-react, radix via `@rentweb/ui`).
- Manual check with curl: `curl -s -H "Host: demo-shop.localhost:3000" http://localhost:3000/products | head`.
- Visual check: `pnpm --filter @rentweb/tooling screenshot -- demo-shop --path /products` → `tooling/screenshots/*.png` (open with Read). Check desktop AND mobile output: no horizontal scroll, 44px touch targets, readable contrast.
- Re-seed your demo tenant after changing its template seed: `pnpm --filter @rentweb/tooling reset-demo -- --template shop`.

## 8. Definition of done

- Every storefront page in the brief exists, renders real data from the demo tenant, works on 390px and 1440px, and the full customer journey completes end-to-end (browse → act → pay → confirmation → account history).
- Sections registered; demo template home page renders them (no "ยังไม่มีคอมโพเนนต์" placeholders).
- Services covered by tests for the money/stock/slot-critical paths; typecheck green.
- Final report lists: files created, routes, how to test, anything shared you needed but could not change.
